## 1. 核心原则

### 1.1 AI 对话底层逻辑
- **AI 不会读心术**：你给多少上下文，它就理解多少；模糊输入 = 随机输出。
- **AI 擅长模式匹配**：提供参考格式、示例代码、错误日志，它会模仿并收敛。
- **AI 需要明确约束**：不设定输出格式、语言、长短，答案可能“跑偏”或冗余。
- **迭代才是生产力**：第一次回答很少完美，通过追问逐步逼近目标。

### 1.2 高效提问三要素
| 要素 | 说明 | 反例 |
|------|------|------|
| **上下文** | 项目背景、运行环境、错误日志、相关代码片段 | “我的代码跑不起来” |
| **目标** | 期望结果（修复、新增功能、优化性能等） | “帮我看看这段代码” |
| **约束** | 格式要求、技术栈限制、性能阈值、避免的操作 | “随便写” |

## 2. 提示词基础框架

**万能公式**：
```
角色 + 背景 + 需求 + 约束 + 输出格式 + 示例（可选）
```

### 2.1 完整示例
```text
角色：你是一名资深的 Python Flask 全栈工程师。
背景：我有一个体育场人群检测系统，后端用 Flask + ONNX 模型推理，前端 HTML/JS 三步工作流（裁剪→检测→重建）。
需求：在检测页面增加一个“浏览”按钮，让用户可以选择本地文件夹并上传到服务器临时目录。
约束：
- 不要修改已有的 auto-detect 逻辑；
- 后端 API 路径为 /api/upload_folder_for_detect；
- 前端按钮样式需与现有按钮一致；
- 上传后自动更新输入框路径。
输出格式：给出修改后的 detect.html 和 detect.js 完整代码。
```

### 2.2 各要素详解
- **角色**：设定身份可激活 AI 相应的知识域和语言风格（例如“十年经验后端”或“严谨的学术专家”）。
- **背景**：提供上下文，避免 AI 猜测。包含技术栈、现有架构、文件结构、当前遇到的问题。
- **需求**：用一句话明确你要什么（“增加一个浏览按钮”），然后展开细节。
- **约束**：非常重要！如“必须兼容 Python 3.7”“不要使用 jQuery”“保持现有代码风格”。
- **输出格式**：指定“完整代码块”“补丁文件 diff”“点列表”等，避免 AI 长篇大论解释。
- **示例**：提供一个类似的输入输出能极大提升准确率，尤其在格式要求严格时。

## 3. 结构化提问技巧

### 3.1 拆分问题
大问题拆成多个小问题，逐个击破。  
**使用场景**：功能复杂、涉及多个文件/步骤。

```text
步骤1：先帮我把 detect.html 中的按钮加上，样式用 btn-secondary。
步骤2：然后给出 detect.js 中浏览按钮的上传逻辑。
步骤3：最后在后端添加对应的 Flask 接口。
```

**对话中对应**：裁剪页自动检测问题 → 拆分为“删除自动检测代码”“添加浏览按钮”“补后端接口”三步解决。

### 3.2 限定范围
明确文件、函数、变量名，避免 AI 改动无关代码。  
```text
仅修改 detect.js 中“自动开始检测”那段 setTimeout 逻辑，其他地方不动。
```

### 3.3 指定格式
要求输出形式：完整文件代码、diff 补丁、表格、点列表、伪代码等。  
```text
请以 diff 格式输出改动，方便我直接应用。
```

### 3.4 设定身份
让 AI 模拟特定角色，答案更专业。  
```text
你是一名前端架构师，请用现代 JavaScript (ES6+) 重写此模块。
```

## 4. 优化迭代技巧

### 4.1 追问修正
第一次答案不完全满意时，直接指出问题并要求修正。
```text
你给的代码中 stand 变量使用了小图文件名，应该是映射表中的原始看台名，请修正。
```

### 4.2 补充上下文
若 AI 因缺少背景而跑偏，补充日志、错误信息、目录结构。
```text
补充服务器后端日志：
📁 读取了 0 个 JSON 文件，总计 0 个检测框（还原前）
由此看来，JSON 文件未被找到，因为检测结果文件夹是平铺结构，请修改查找逻辑。
```

### 4.3 分段输出
处理长内容时，要求先输出大纲或关键部分，确认后再展开。
```text
先列出需要修改的文件和接口名称，我确认后再逐文件给出代码。
```

### 4.4 精简/扩写控制
- **精简**：说“只需关键代码，不要解释”。
- **扩写**：说“详细解释每一步的原理和选择原因”。

## 6. 避坑指南

| 常见问题 | 后果 | 解决方法 |
|----------|------|----------|
| 模糊提问：“帮我写个功能” | 得到不相关或无法使用的代码 | 提供背景+需求+约束 |
| 信息缺失：不贴日志、不贴代码 | AI 猜测错误，反复循环 | 提供最小可复现样例 |
| 无格式约束：“写个网页” | 输出几千字解释而非代码 | 指定“完整 HTML 文件” |
| 一次提太多：“帮我完成整个系统” | 答案浅尝辄止，逻辑混乱 | 拆分为步骤，逐步完善 |
| 忽略版本约束：“用最新技术” | 产生不兼容语法 | 明确 Python 3.6、ES5 等 |
| 不检查 AI 的假设 | 被动接受错误方案 | 结合自身项目上下文验证 |

**重要提醒**：AI 会“顺着你的话”生成内容，如果你提问时隐含错误假设，AI 不会主动纠正，只会生成更符合错误假设的答案。**所以，当问题诊断不清时，先让 AI 帮你分析可能原因，再要求修改。**

## 7. 通用万能提示词模板

可直接复制替换 `[...]` 部分，套用到 90% 的技术任务中。

### 7.1 修改已有代码
```text
角色：[你的角色]
背景：[技术栈、项目结构、关键文件]
目标：修改 [具体文件/函数] 以实现 [功能]，并解决 [bug/错误]。
约束：
- 不要修改 [其他功能/文件]
- 输出 [完整代码/diff]
- 保持现有代码风格
附加信息：
[遇到的错误日志]
[相关代码片段]
```

### 7.2 从零开发功能
```text
角色：[你的角色]
背景：新建项目，技术栈为 [语言/框架/库]，目录结构为 [简要说明]。
需求：开发一个 [功能模块]，具体要求：
1. [功能点1]
2. [功能点2]
约束：
- 数据库使用 [SQLite/MySQL]
- API 风格 RESTful
- 前端使用 [React/Vue]
输出格式：先列出需要创建的文件清单，再逐个给出代码。
```

### 7.3 故障排查
```text
角色：资深运维工程师
我的环境：[OS, 软件版本, 配置]
问题表现：[详细错误描述]
已尝试：[你尝试过的操作]
相关日志：
[粘贴完整日志]
要求：分析可能的根本原因，并按可能性从高到低列出解决方案。
```

## 8. 附录：案例还原

本手册源自一个真实的多轮 AI 协作案例：**体育场人群检测系统**开发。

### 8.1 问题与解决路径
| 问题 | 提问方式 | AI 回答 | 最终方案 |
|------|----------|---------|----------|
| 裁剪后自动开始检测 | 给出 detect.js 全文，指明“还没点开始检测就自己开始了” | 定位到 setTimeout 自动调用，建议删除 | 修改 detect.js，移除自动执行逻辑 |
| 增加浏览按钮 | 提供 detect.html 和当前截图，要求“在输入框右边加浏览并选择文件夹的按钮” | 给出 HTML 修改和 JS 上传逻辑，并提示需后端接口 | 添加按钮和隐藏 input，补充 JS 和后端 API |
| 重建时找不到 JSON | 提供重建日志“读取了 0 个 JSON”，说明使用了浏览上传的平铺文件夹 | 分析因目录结构不匹配导致，给出两种方案 | 选择方案二，修改重建 API 兼容平铺模式 |
| stand 名错误 | 指出“stand 变量用了小图文件名”，要求修正 | 提供了新的 rebuild 代码，使用映射表中的正确 stand | 替换代码，最终正确合并检测框并找到原始大图 |

### 8.2 对话技巧总结
- **始终附带文件内容或日志**：让 AI 看到全部上下文。
- **逐步迭代，每次只提一个明确修改点**。
- **在发现隐患时主动告知约束**：例如“不要破坏现有自动带入功能”。
- **当 AI 误解时立即纠正**：例如 stand 名错误，直接指出并要求重写。
